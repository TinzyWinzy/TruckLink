5. REGULATORY SOURCE MODEL
============================================================

Create a first-class regulatory source entity.

interface RegulatorySource {
  id: string;

  title: string;
  instrumentType:
    | "ACT"
    | "STATUTORY_INSTRUMENT"
    | "REGULATOR_NOTICE"
    | "REGULATOR_GUIDANCE"
    | "FORM"
    | "INTERNAL_POLICY";

  instrumentNumber?: string;

  issuingAuthority: string;

  jurisdiction: string;

  publicationDate?: string;
  effectiveDate?: string;

  canonicalReference?: string;
  sourceUrl?: string;

  sourceTier: "A" | "B" | "C" | "D";

  hash?: string;

  version: string;

  status:
    | "DISCOVERED"
    | "AWAITING_VERIFICATION"
    | "VERIFIED"
    | "ACTIVE"
    | "SUPERSEDED"
    | "REPEALED";

  notes?: string;
}

Source hierarchy:

TIER A
Official Gazette, Acts, Statutory Instruments,
official regulator publications/forms/APIs.

TIER B
High-quality legal repositories.

TIER C
Verified company procedures, operational interviews,
pilot data and approved internal policy.

TIER D
Discovery sources only:
news, general web sources, AI extraction, unverified commentary.

IMPORTANT:

A Tier D source must NEVER directly create an ACTIVE blocking control.

AI extraction may generate PROPOSED controls only.

Human verification is required before a regulatory control becomes ACTIVE.

8. DETERMINISTIC RULE ENGINE
============================================================

This is a critical requirement.

Compliance decisions MUST be deterministic.

Do not use an LLM for:

- statutory threshold calculation;
- PASS/FAIL;
- legal applicability;
- release authorization;
- penalty calculation;
- override authorization.

Build a rules evaluator.

Conceptually:

evaluate(
    RegulatoryEvent,
    RegulatoryContext,
    ActiveRuleSet
): RegulatoryEvaluation

Return:

interface RegulatoryEvaluation {
  id: string;

  eventId: string;
  rulesetVersion: string;

  decision:
    | "PASS"
    | "PASS_WITH_WARNINGS"
    | "HOLD"
    | "QUARANTINE"
    | "REVIEW_REQUIRED";

  controlsEvaluated: number;
  passed: number;
  warnings: number;
  failed: number;

  results: RegulatoryControlResult[];

  evaluatedAt: string;
}

Every result must explain:

- rule evaluated;
- applicability;
- input value;
- expected condition;
- result;
- source;
- source provision where available;
- rule version;
- evidence;
- remediation/action.

9. RULE VERSIONING
============================================================

Rules must be versioned.

Never silently overwrite historical regulatory logic.

Example:

ZW-TRN-LOAD-014
v1.0
ACTIVE_FROM = date

Later:

ZW-TRN-LOAD-014
v1.1

Historical dispatches retain the exact rule version applied at the time.

A Compliance Passport must therefore remain reproducible.

Implement:

RuleSetVersion

with:

- version;
- createdAt;
- activatedAt;
- retiredAt;
- rules;
- approval;
- change summary.

→ regulatory source
→ version
→ required evidence/action.

ACCEPTANCE 3 — APPLICABILITY

Given two vehicles with different operational contexts,
when pre-dispatch evaluation occurs,
then they may receive different applicable control sets.

ACCEPTANCE 4 — DETERMINISM

Given identical event data and identical active ruleset,
when evaluation is run repeatedly,
then the regulatory decision is identical.

ACCEPTANCE 5 — VERSIONING

Given a rule changes,
when a new ruleset is activated,
then historical evaluations remain attached to the previous ruleset.

ACCEPTANCE 6 — QUARANTINE

Given a blocking failure,
when the vehicle is quarantined,
then it cannot be released through the normal path until remediation,
re-evaluation and required approval are completed.

ACCEPTANCE 7 — NO SELF APPROVAL

Given Supervisor A requests an override,
when Supervisor A attempts to approve it,
then approval is denied.

ACCEPTANCE 8 — COMPLIANCE PASSPORT

Given a successfully released vehicle,
then the system produces a passport containing:

trip;
vehicle;
driver;
controls;
evidence;
approvals;
ruleset version;
timestamps.

ACCEPTANCE 9 — REGULATORY WATCH

Given a proposed regulatory change,
then it cannot become ACTIVE without the configured human verification step.

ACCEPTANCE 10 — NO FAKE LAW

Given a regulatory threshold is not verified/configured,
then the system displays CONFIGURATION REQUIRED
instead of inventing a legal threshold.

ACCEPTANCE 11 — COPILOT SAFETY

Given the user asks the Copilot whether an unverified load is "legally compliant,"
then the Copilot must retrieve/display the deterministic system state
and must not invent a legal conclusion.

ACCEPTANCE 12 — OFFLINE VERSION INTEGRITY

Given a regulatory evaluation occurs offline,
then its ruleset version remains attached after synchronization.

ACCEPTANCE 13 — DASHBOARD INTEGRITY

Given executive metrics are displayed,
then each metric can be derived from underlying demo/application records.

No hardcoded fake KPI totals.
