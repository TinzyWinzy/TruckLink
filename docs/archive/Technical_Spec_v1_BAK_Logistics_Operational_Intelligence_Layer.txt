1. Document Purpose

This Technical Specification defines the architecture, technology stack, data models, API contracts, security posture, and deployment strategy for the BAK Logistics Operational Intelligence Layer. It is intended for the engineering team, DevOps, and technical stakeholders at BAK Logistics.


2. Architecture Philosophy

The system is designed as a lean, non-disruptive intelligence overlay. It operates entirely independently of BAK's existing WMS/ERP during the pilot, with a forward-compatible architecture for Phase 2 integration.

Core Principles:
- Offline-first: Yard operations cannot pause for connectivity issues
- Event-driven: All state changes emit events for real-time dashboards and audit trails
- Immutable audit: Compliance logs are append-only with cryptographic integrity
- Multi-tenant: Database design supports future rollout across multiple BAK facilities
- API-ready: RESTful and GraphQL interfaces pre-built for Phase 2 WMS/ERP sync

5.2 Indexes

Required Firestore Composite Indexes:
- queue: facilityId + status + entryTimestamp (for live queue filtering)
- queue: facilityId + assignedSupervisorId + status (for supervisor workload view)
- complianceChecks: facilityId + overallStatus + completedAt (for compliance reporting)
- auditLogs: facilityId + timestamp (for audit trail queries)
- alerts: facilityId + status + severity + triggeredAt (for active alert dashboard)

5.3 Data Integrity Rules

- Queue entries cannot transition from RELEASED or QUARANTINED back to QUEUED
- Dock status must be AVAILABLE before assignment
- Compliance check cannot be created for a queue entry not in LOADING or COMPLETED status
- Override approval requires a different user than the override requester
- Audit logs are append-only: no update or delete operations permitted

7. Security Architecture

7.1 Authentication Flow

1. User enters credentials (email/password or PIN) on tablet/desktop
2. Client sends credentials to Firebase Auth
3. Firebase Auth verifies and returns JWT ID token (24-hour expiry) and refresh token
4. Client stores token in secure HTTP-only cookie or secure local storage
5. All API requests include Authorization: Bearer {token} header
6. Firebase Security Rules validate token and enforce RBAC on every database read/write

7.2 Authorization (Firebase Security Rules)

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Users can only read their own profile
    match /facilities/{facilityId}/users/{userId} {
      allow read: if request.auth != null && request.auth.uid == userId;
      allow write: if request.auth != null && getUserRole(request.auth.uid) == 'ADMIN';
    }

    // Queue: supervisors can create/update, managers can read all
    match /facilities/{facilityId}/queue/{queueEntryId} {
      allow create: if request.auth != null && hasRole(['DISPATCH_SUPERVISOR', 'OPERATIONS_SUPERVISOR']);
      allow update: if request.auth != null && hasRole(['DISPATCH_SUPERVISOR', 'OPERATIONS_SUPERVISOR', 'FACILITY_MANAGER']);
      allow read: if request.auth != null && isAssignedToFacility(facilityId);
      allow delete: if false; // No deletes permitted
    }

    // Compliance checks: supervisors create, operations supervisors can override
    match /facilities/{facilityId}/complianceChecks/{checkId} {
      allow create: if request.auth != null && hasRole(['DISPATCH_SUPERVISOR']);
      allow update: if request.auth != null && hasRole(['OPERATIONS_SUPERVISOR', 'ADMIN']);
      allow read: if request.auth != null && isAssignedToFacility(facilityId);
      allow delete: if false;
    }

    // Audit logs: append-only, no deletes, no updates
    match /facilities/{facilityId}/auditLogs/{logId} {
      allow create: if request.auth != null && isSystemOrAuthenticated();
      allow read: if request.auth != null && hasRole(['COMPLIANCE_OFFICER', 'ADMIN', 'EXECUTIVE']);
      allow update, delete: if false;
    }

    // Alerts: all authenticated facility users can read and acknowledge
    match /facilities/{facilityId}/alerts/{alertId} {
      allow read: if request.auth != null && isAssignedToFacility(facilityId);
      allow update: if request.auth != null && isAssignedToFacility(facilityId);
      allow create, delete: if false;
    }
  }
}

7.3 Data Encryption

- Data in transit: TLS 1.3 (enforced by Firebase Hosting and Cloud Functions)
- Data at rest: AES-256 (enforced by Google Cloud Firestore and Cloud Storage)
- Passwords: bcrypt hashing with cost factor 12
- API tokens: JWT signed with RS256, 24-hour expiry
- Audit log chain: Each entry hashes previous entry's hash + current payload using SHA-256

7.4 Audit Log Integrity

Implementation of cryptographic chain:
1. First log entry: hash = SHA-256(entry_payload + facility_salt)
2. Subsequent entries: hash = SHA-256(previous_hash + entry_payload + facility_salt)
3. Export includes all hashes and facility salt for third-party verification
4. Tampering detection: recompute hash chain and compare with stored hashes

7.5 Input Validation

- All API inputs validated using Zod schemas on Cloud Functions
- SQL injection prevention: NoSQL database (Firestore) inherently resistant
- XSS prevention: React auto-escapes output; CSP headers enforced
- File upload validation: Images only (JPEG, PNG), max 5MB, scanned for malware


8. Offline-First Architecture

8.1 Offline Strategy

The system must function fully during network outages common in industrial yard environments.

8.2 IndexedDB Schema (Client-Side)

Database: radbit_bak_offline
Object Stores:
- pendingActions: { id, actionType, payload, timestamp, retryCount, lastError }
- cachedQueue: { facilityId, entries, lastSyncedAt }
- cachedDocks: { facilityId, docks, lastSyncedAt }
- cachedEquipment: { facilityId, equipment, lastSyncedAt }
- cachedUsers: { userId, profile, lastSyncedAt }
- settings: { key, value }

8.3 Sync Mechanism

1. User performs action while offline (e.g., completes compliance check)
2. Action stored in pendingActions with unique client-generated ID
3. Service worker detects online event
4. Background sync API triggers sync process
5. Client processes pendingActions in chronological order
6. Each action sent to Cloud Function with idempotency key (client-generated ID)
7. Cloud Function checks idempotency: if action ID already processed, return cached result
8. On success: remove from pendingActions, update cached data
9. On failure: increment retryCount, store lastError, retry with exponential backoff (max 5 retries)
10. Conflict resolution: server timestamp wins; client notified of resolved state

8.4 Offline UI States

- Clear connectivity indicator (green/amber/red) in app header
- Offline badge on actions that will be queued
- Sync progress indicator when reconnecting
- Warning modal if user attempts to navigate away during active sync


9. Real-Time Architecture

9.1 Firestore Listeners

- Live Queue Dashboard: listens to queue collection filtered by facilityId + active statuses
- Dock Status Board: listens to docks collection filtered by facilityId
- Alert Panel: listens to alerts collection filtered by facilityId + ACTIVE status
- Equipment Tracker: listens to equipment collection filtered by facilityId

9.2 Listener Optimization

- Use query cursors and pagination for large datasets (>100 documents)
- Detach listeners when components unmount to prevent memory leaks
- Batch UI updates using React Query's batching to prevent render thrashing
- Implement optimistic updates for user actions (show result immediately, confirm with server)

9.3 Event-Driven Processing (Cloud Functions)

onQueueEntryCreated:
  - Calculate initial wait time
  - Update facility active vehicle count
  - Emit queue.entry.created event

onQueueEntryStatusChanged:
  - If status = ASSIGNED: update dock status, calculate assignment time
  - If status = COMPLETED: calculate turnaround time, update performance metrics
  - If status = QUARANTINED: create CRITICAL alert, notify Operations Supervisor
  - Emit queue.entry.status_changed event

onComplianceCheckCompleted:
  - If overallStatus = FAIL: create quarantine alert, block gate release
  - If overallStatus = PASS: enable gate release, log completion
  - Update compliance statistics
  - Emit compliance.check.completed or compliance.check.failed event

onAlertCreated:
  - If severity = CRITICAL: immediate SMS + email to Operations Supervisor
  - If severity = HIGH: email + in-app notification
  - If not acknowledged within 10 minutes: escalate to Facility Manager
  - If not acknowledged within 30 minutes: escalate to Executive


10. Compliance Validation Engine

10.1 Axle Load Calculation

Input: axleConfiguration (string), measuredWeights (array of numbers), route (string)
Logic:
1. Parse axle configuration (e.g., "2-4-2" = 3 axles, positions 1, 2, 3)
2. Retrieve route-specific limits from configuration (stored in facility document)
3. For each axle: measuredWeight <= limit ? PASS : FAIL
4. Calculate total weight = sum(measuredWeights)
5. Retrieve vehicle GVM rating from vehicle document
6. totalWeight <= gvmRating ? PASS : FAIL
7. overallStatus = ALL(axleStatus = PASS) AND gvmStatus = PASS ? PASS : FAIL

10.2 Configuration-Driven Rules

Stored in facilities/{facilityId}/complianceConfig:
- axleLimits: map<route, array<{ axlePosition, maxWeight }>>
- gvmLimits: map<vehicleType, maxWeight>
- requiredChecklistItems: array<{ itemId, label, mandatory, requiresPhoto }>
- overridePolicy: { requiresSecondaryApproval: boolean, autoEscalateAfterMinutes: number }

10.3 Override Workflow

State Machine:
  PASS/FAIL -> (FAIL detected) -> QUARANTINED
  QUARANTINED -> (override requested) -> PENDING_OVERRIDE
  PENDING_OVERRIDE -> (approved) -> OVERRIDE_APPROVED
  PENDING_OVERRIDE -> (rejected) -> QUARANTINED
  OVERRIDE_APPROVED -> (gate release) -> RELEASED

All state transitions logged in audit trail with full context.


11. Performance Engineering

11.1 Database Optimization

- Use Firestore batched writes for multi-document updates (max 500 per batch)
- Implement pagination for all list queries (default 25 items, max 100)
- Use Firestore transactions for atomic operations (e.g., dock assignment + queue status update)
- Denormalize computed fields (waitTime, turnaroundTime) to reduce client-side calculation
- Set TTL policies on temporary data (e.g., expired sessions, old pendingActions after sync)

11.2 Frontend Optimization

- Code splitting by route (lazy load Dashboard, Compliance, Reports, Admin modules)
- Image optimization: WebP format, responsive sizing, lazy loading
- Bundle size target: <200KB initial JS, <500KB total after lazy loading
- Virtualized lists for queue entries (>50 items)
- Debounce search inputs (300ms)
- Memoize expensive computations (useMemo for analytics calculations)

11.3 API Optimization

- Cloud Functions cold start mitigation: minimum instances = 1 during operational hours
- Response caching: Cache-Control headers for static configuration data (1 hour TTL)
- Compression: Brotli compression for API responses >1KB
- Connection pooling: Reuse Firestore client instances across function invocations

11.4 Load Testing Targets

- 50 concurrent users per facility
- 100 queue entries created per hour per facility
- 200 compliance checks completed per hour per facility
- Dashboard load time: <2 seconds on 3G
- API response time: p95 <500ms for read operations, p95 <1s for write operations


12. Error Handling & Resilience

12.1 Client-Side Error Handling

- Global error boundary catches React rendering errors, displays fallback UI, logs to Sentry
- API error mapping: HTTP status codes mapped to user-friendly messages
- Network errors: automatic retry with exponential backoff (3 attempts)
- Validation errors: inline field-level feedback with Zod error messages
- Sync failures: persistent notification with retry option and error details

12.2 Server-Side Error Handling

- Cloud Functions: structured logging with correlation IDs
- Unhandled exceptions: caught by Firebase, logged, function instance recycled
- Firestore transaction failures: automatic retry (max 3 attempts), then fail with error code
- External service failures (SMS/email): queue for retry, alert admin if persistent

12.3 Graceful Degradation

- If real-time listener fails: fall back to manual refresh button
- If analytics aggregation fails: show cached data with stale timestamp warning
- If compliance validation service fails: block gate release (fail-safe) and alert admin
- If alert dispatch fails: queue alerts, display in-app banner

- OWASP ZAP automated scan (staging environment)

- Firebase Security Rules unit tests (100% coverage of all paths)

17. Disaster Recovery

17.1 Backup Strategy

- Firestore: Daily automated backups (Google Cloud managed)
- Cloud Storage: Object versioning enabled, 7-year retention for compliance
- Configuration: Infrastructure-as-code (Firebase CLI config) stored in Git

17.2 Recovery Procedures

RPO (Recovery Point Objective): <1 hour
RTO (Recovery Time Objective): <4 hours

1. Identify failure scope (data corruption, region outage, accidental deletion)
2. Assess backup integrity from most recent daily backup
3. Restore Firestore from backup to staging for validation
4. If validation passes, restore to production
5. Verify data consistency with checksum comparison
6. Notify stakeholders and document incident
